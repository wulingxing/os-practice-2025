学习内容

学习笔记
1. 线性模型与加权评分

线性模型的基本形式为 f(x) = w₁x₁ + w₂x₂ + ... + b，即通过对各特征加权求和得到预测值。

在本人的毕设系统中，智能体评分算法本质上就是一个简化的线性模型：

text
总分 = 0.7 × 技能匹配度 + 0.3 × 可靠性分数
其中技能匹配度与可靠性分数为输入特征，权重系数（0.7 和 0.3）为模型参数。这种设计的优势在于可解释性强——每一分都能追溯来源，便于向用户解释调度结果。这与线性模型的核心价值一致：简洁、透明、易于理解。

2. 决策树与调度规则

决策树通过一系列 if-else 规则对样本进行分类。在毕设系统的报名模块中，三种招募模式的处理逻辑也呈现类似的树形结构：

顺序录取模式 → 有名额则直接录取，无名额则候补

评分择优模式 → 报名截止后按总分排序录取

面试筛选模式 → 评分筛选后进入面试环节

这种基于规则的分支逻辑与决策树的决策过程相似，只是本系统的规则由人工预设，而非从数据中学习得到。如果未来有足够的调度数据积累，可以考虑引入决策树算法来自动发现最优的调度规则。

学习心得
通过对照学习，我更清晰地认识到自己毕设系统的智能体调度算法在人工智能领域中的定位——它是一种基于规则的专家系统，具有强可解释性，适用于数据量较小的场景。后续研究可探索引入机器学习方法，从历史调度数据中学习最优的权重配置，实现自适应优化。

三、遇到的问题及解决方法
问题一：前后端数据未能正确传递
问题描述：个人中心页面无法显示用户信息（昵称、角色等），排查发现是因为模板自带的 Pinia store 和我们手动写入的 localStorage 使用了同一个 key（user），导致数据互相覆盖。

解决方法：将我们登录时写入的 localStorage key 从 user 改为 app-user，与 Pinia 的存储键区分开，解决了数据覆盖问题。

问题二：数据库枚举值与模型不匹配
问题描述：活动列表接口调用时报错，原因是数据库 activities 表的 status 枚举值仍是旧版本（包含 pending_review、open、closed 等），而后端模型已更新为新版本（draft、pending、published、rejected）。

解决方法：执行 SQL 语句将 status 列改为新枚举值，并更新了已有数据的状态映射。
